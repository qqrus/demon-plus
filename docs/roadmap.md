## Ключевые решения для этапа 2

1. Проверить лицензию и официальный путь получения Olist. Секреты скачивания
   не записывать в код или Git; предусмотреть инструкцию ручной загрузки.
2. Выбрать определение целевой величины и правила обработки отмен/возвратов.
   Итоговый статус заказа может быть неизвестен на историческую дату прогноза:
   учитывать это при реконструкции срезов и документировать ограничения.
3. Изучить период полной выгрузки и плотность категорий. Не считать любой пропуск
   нулевой продажей; не выбирать категории по будущему тестовому периоду.
4. Зафиксировать временные срезы и финальный тест до подбора модели.
5. Сравнить повтор последней недели и среднее четырёх недель для всех горизонтов.

## Границы MVP

Основной прогноз — по категориям. Отдельные товары — только после проверки истории.
Основная модель — CatBoost; сравнение может показать, что baseline лучше.
Запасы подаются отдельно; синтетические значения явно маркируются.
SQLite выбран для локального запуска, переход на PostgreSQL требует миграций и тестов.
Переобучение не означает автоматическую замену действующей модели.
Data drift служит сигналом, quality drift оценивается по сохранённым прогнозам и фактам.

Никакого push или PR без отдельного явного подтверждения пользователя.
