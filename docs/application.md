# Локальное приложение

После `fetch-data` и `train` запустите в двух терминалах из корня репозитория:

```bash
uv run --locked uvicorn demon_plus.api.app:create_app --factory --host 127.0.0.1 --port 8000
uv run --locked streamlit run src/demon_plus/ui/app.py --server.address 127.0.0.1 --server.port 8501 --server.headless true
```

Откройте http://127.0.0.1:8501. Swagger: http://127.0.0.1:8000/docs.
Первый запуск создаёт неизменяемую версию истории до даты обучения модели.
В текущем демо это 2018-06-30. Это исторический прогноз, не прогноз на сегодняшний день.

## Разделы интерфейса

- **Прогноз:** категория, 7/14/30 дней, история и прогноз на графике, выгрузка CSV.
- **Запасы:** редактируемые остатки, целевой запас и датированные поставки.
  Начальные значения синтетические и явно помечены. Поставки поступают в начале дня.
  Отрицательный баланс переносится как неудовлетворённый спрос. Первый день дефицита
  сохраняется, даже если поздняя поставка восстановит запас. Излишек — превышение
  целевого остатка в конце горизонта. При наличии дефицита статус имеет приоритет.
- **Данные:** шаблон, загрузка продаж, запуск переобучения и отдельное применение модели.
- **Качество:** MAE, RMSE, WAPE исходной модели на валидации и итоговом тесте.
  После замены модели эти исторические метрики не выдаются за метрики новой модели.
  Автоматический drift monitoring добавляется на этапе 5.

## Контракт продаж

UTF-8 CSV с колонками строго `date,category,units`, не более 5 MB по умолчанию.
`date` — YYYY-MM-DD, `category` — исходный код категории Olist,
`units` — конечное неотрицательное целое число. Для каждого нового дня нужны
все категории, в том числе явные нули. Даты должны идти без пропусков после истории.
Совпадающие строки идемпотентны; конфликтующие дубли и исправления прошлого отклоняются.
Новые категории требуют отдельного изменения модели и сейчас не принимаются.

Для демонстрации подготовьте реальные июльские продажи:

```bash
uv run --locked python -m demon_plus.data.demo_update
```

Загрузите `data/demo/sales-update.csv` в разделе «Данные». Файл добавит 30 дней
для исходной модели. Это повторное использование исторического holdout для демонстрации
обновления, **не новый независимый тест**. Исходные benchmark-отчёты не меняются.

Для переобучения нужно 30 новых дней после обучения активной модели. Последние 30 дней
используются как операционное окно сравнения. Параметры CatBoost берутся из активной
модели; кандидат обучается без этого окна и сравнивается на нём с текущей моделью
и средним за 28 дней. Кандидат допускается к применению, если WAPE не хуже обоих.
После сравнения он обучается на всей доступной истории и сохраняется в MLflow.
Применение требует отдельного действия и отклоняется, если данные или модель
с тех пор изменились. Нулевая сумма фактов делает WAPE неопределённым: продвижения нет.

## API и хранение

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | Готовность и инструкция при отсутствии модели |
| GET | `/api/v1/status` | Категории, даты и активные версии |
| POST | `/api/v1/forecasts` | Прогноз; тело: category, horizon |
| GET | `/api/v1/forecasts/{id}` | Ранее сохранённый прогноз |
| POST | `/api/v1/inventory` | Сценарий запасов и поставок |
| GET | `/api/v1/sales/template` | Шаблон следующего дня |
| POST | `/api/v1/sales` | Multipart CSV, поле file |
| GET | `/api/v1/metrics` | Исторические отчёты исходной модели |
| GET | `/api/v1/jobs` | Задачи переобучения |
| POST | `/api/v1/jobs/retrain` | Фоновое обучение, ответ 202 |
| POST | `/api/v1/jobs/{id}/activate` | Применение допущенного кандидата |

SQLite через SQLAlchemy хранит состояние, метаданные версий, прогнозы и задачи.
CSV-версии получают SHA-256 и сохраняются отдельно в `data/versions`;
прогноз привязан к версии данных и модели. Модель и статус её применения
обновляются одной транзакцией. Исходные данные и модели не попадают в Git.

Настройки: `DEMON_PLUS_APP_DB`, `DEMON_PLUS_API_URL`, `DEMON_PLUS_MAX_UPLOAD_BYTES`
в `.env`; образец — `.env.example`. HTTP-журнал содержит request ID, путь и статус,
но не строки загруженного CSV.

Запускайте **один процесс API без нескольких workers**. Блокировка и очередь обучения
работают внутри процесса; прерванная задача при перезапуске помечается ошибкой.
Это локальное приложение без аутентификации. Для нескольких пользователей потребуются
отдельная очередь, миграции БД, контроль конкурентных обновлений и авторизация.
SQLAlchemy упрощает переход к PostgreSQL, но такой переход ещё не реализован.
