# Мониторинг: что именно измеряем

Раздел «Качество» автоматически обновляет отчёт при открытии после изменения продаж,
модели, сохранённых прогнозов или настроек порога. API: `GET /api/v1/monitoring`.
Результаты кэшируются по этим версиям и сохраняются как JSON в `artifacts/monitoring`.
Планировщика и внешних уведомлений нет: оценка запускается по запросу.

## Data drift

Evidently 0.7 сравнивает распределения **дневных продаж каждой категории**.
Это мониторинг входной истории спроса, не полный мониторинг всех производных
признаков CatBoost. Изменение распределения не означает автоматически ошибку модели.

- Reference: последние 28 дней до даты обучения активной модели.
- Current: последние 28 дней фактов, полностью после даты обучения.
- Метод: расстояние Wasserstein, делённое на `max(std(reference), 0.001)`.
  Недели представлены поровну, поскольку окно содержит ровно четыре недели.
- Порог каждой категории: `max(0.1, 1.1 × 95-й перцентиль исторических расстояний)`.
  Исторические расстояния рассчитаны между соседними 28-дневными блоками до обучения.
  Новые данные не участвуют в подборе порогов. Число калибровочных окон видно в отчёте.
- При хотя бы одной категории выше порога показывается предупреждение.
  Это эвристический сигнал для проверки, не статистическая гарантия и не p-value.
- Нужны минимум 84 дня исходной истории и 28 новых дней. Иначе статус `waiting`.
  После применения новой модели reference меняется и сбор новых фактов начинается заново.

HTML-отчёт создаёт сам Evidently; скачать его можно из интерфейса или через
`GET /api/v1/monitoring/html`. Счётчики телеметрии Evidently отключены.
Метод и API: [официальная документация Evidently](https://evidentlyai.github.io/evidently/api-reference/main/evidently/core/report.html).

Порог откалиброван на доступной истории, но не проверен на большом количестве
реальных инцидентов. Тренд, акции и сезонность могут давать законные срабатывания.
В production нужны отдельные пороги по сезонам и оценка ложных тревог.

## Quality drift

Используются только **ранее сохранённые прогнозы**: при поступлении фактов сервис
не пересчитывает прогноз прошлой даты новой моделью. Даты соединяются с фактами;
пропущенные факты не заменяются нулями, неполный горизонт остаётся `waiting`.

Прогнозы группируются по `(model_id, category, horizon)`. Повторный запрос на том же
срезе не увеличивает выборку. Reference — первый полностью наблюдённый прогноз;
current — последний полный прогноз, цели которого не пересекаются с reference.
Показаны даты обоих срезов, число полных/ожидающих прогнозов, MAE, RMSE и WAPE.
Ошибки разных моделей и горизонтов не смешиваются.

Один полный прогноз получает статус `reference_only`: метрики есть, сравнения пока нет.
Если сумма фактов одного окна равна нулю, WAPE не определён и сравнение получает
статус `undefined`. Ухудшение фиксируется, когда текущий WAPE превышает одновременно
reference на 25% относительно и на 5 процентных пунктов абсолютно:
`current > max(reference × 1.25, reference + 5)`.
Пороги задаются в `.env` через `DEMON_PLUS_QUALITY_RELATIVE_INCREASE`
и `DEMON_PLUS_QUALITY_ABSOLUTE_INCREASE`.

Эти пороги — прозрачное начальное правило, **не откалиброванный статистический тест**.
Первое окно может оказаться нетипичным; для production нужны несколько окон,
оценка доверительных интервалов и согласование допустимой бизнес-ошибки.
Для новой модели сначала накапливается собственная история прогнозов и фактов.
Старые группы остаются в отчёте с собственным model_id.

## Демонстрация

1. На исходной истории до июня сохраните прогноз категории на 7 дней.
2. Создайте `sales-update.csv` по инструкции приложения, загрузите сначала 7 дней.
3. Сохраните новый прогноз той же категории на 7 дней, загрузите следующие 7 дней.
4. Откройте «Качество»: оба горизонта уже имеют факты и могут сравниваться.
5. Загрузите оставшийся июль: станет доступен отчёт распределений продаж.

Это историческая демонстрация, а не новые независимые результаты качества модели.
Автотесты отдельно проверяют отсутствие сдвига, резкий сдвиг, ухудшение ошибки,
нулевые продажи, неполные факты, дубли, смену модели и пересекающиеся окна.

## Зависимости

Evidently 0.7 требует Plotly 5.24; Litestar ограничен версией ниже 2.23 из-за
устаревшего API внутри Evidently. При импорте Evidently локально подавляются только
известные предупреждения о `numpy.core` и escape-последовательностях его docstring.
Остальные предупреждения при тестировании считаются ошибками.
