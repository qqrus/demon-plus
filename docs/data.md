# Данные и контракт этапа 2

Источник: [Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce),
автор Olist, версия 2. Лицензия источника —
[CC BY-NC-SA 4.0](https://creativecommons.org/licenses/by-nc-sa/4.0/).
Это данные для некоммерческого учебного проекта; исходные файлы в Git не включены.
Производные таблицы и графики в `docs/results` распространяются с атрибуцией
Olist по CC BY-NC-SA 4.0. Это не назначает лицензию программному коду проекта.

## Получение

```bash
uv run --locked demon-plus fetch-data
```

Загрузчик обращается к публичному Kaggle endpoint с `datasetVersionNumber=2`.
Ключи и вход в аккаунт при проверенном запуске не требовались. Если загрузка
недоступна, скачайте официальный ZIP версии 2 вручную, сохраните его как
`data/raw/olist-v2.zip` и повторите команду. При изменённом `DEMON_PLUS_DATA_DIR`
используйте соответствующий каталог `raw`.

Ожидаемый SHA-256 ZIP:

```text
967e41e04fc306fe604e2a693f488995a8b41e5047418f8a5c8e4abd6deca784
```

При несовпадении обработка останавливается. Не отключайте проверку: другая версия
данных требует отдельного изменения протокола. ZIP кешируется локально. Извлекаются
только четыре разрешённых CSV; произвольные пути архива не используются.
Существующий CSV с отличающимся содержимым не перезаписывается.
`data/raw/manifest.json` фиксирует источник, версию, лицензию и хеши CSV.

## Входные таблицы

CSV с заголовком, UTF-8, разделитель — запятая.
Лишние столбцы допустимы; перечисленные обязательны.

| Файл | Поля | Ключ |
|---|---|---|
| olist_orders_dataset.csv | order_id, order_purchase_timestamp, order_status | order_id |
| olist_order_items_dataset.csv | order_id, order_item_id, product_id | order_id + order_item_id |
| olist_products_dataset.csv | product_id, product_category_name | product_id |
| product_category_name_translation.csv | Справочник для будущего интерфейса | Не используется в расчёте |

Идентификаторы читаются как строки. `order_item_id` — положительное целое число
в текстовом представлении. Каждая уникальная товарная строка — **одна единица**;
`order_item_id` является номером позиции, а не количеством.
Точное совпадение всех полей строки считается дублем и удаляется с подсчётом.
Разные строки с одинаковым ключом вызывают ошибку.

Покупка должна иметь дату `YYYY-MM-DD HH:MM:SS`. Часовой пояс не выдумывается:
используется дата источника без преобразования в UTC. Пропущенные/невалидные даты,
пустые ключи и ссылки на несуществующие заказы/товары вызывают ошибку.
Оба соединения проверяются как many-to-one: они не должны размножать позиции.

Неизвестная категория получает `__unknown__`: единицы сохраняются для аудита,
но такой ряд не участвует в выборе десяти категорий.
Заказы без позиций считаются отдельно; количество для них не придумывается.

## Целевая величина и календарь

Цель — gross ordered units: число заказанных единиц по дате покупки.
Финальный `order_status` используется только в аудите, не в отборе строк или признаках.
Отмены, возвраты, фактическая отгрузка и неудовлетворённый спрос не восстанавливаются.
Статический датасет не содержит времени появления/исправления каждой записи:
мы предполагаем доступность строки заказа и категории на дату покупки.
Это ограничение реконструкции исторического состояния.

Для рабочего окна 2017-01-05—2018-06-30 проверяется наличие продаж магазина
на каждом календарном дне. Затем отсутствующие наблюдения выбранной категории
заполняются нулями. Это предположение о полноте выгрузки; оно не означает,
что товар был в наличии. Дни до первой продажи категории тоже трактуются как
нули заказов; статус её ассортимента в источнике неизвестен.

На выходе `data/processed/category_daily.csv`: колонка `date` и десять колонок
категорий с неотрицательным количеством. Названия категорий — исходные португальские
идентификаторы. Новая универсальная загрузка пользовательских продаж через UI/API
будет добавлена на этапе 4; текущий загрузчик ожидает схему Olist.

## Протокол и артефакты

Настройки периода, срезов и отбора категорий находятся в `.env.example`.
Изменять их можно через `.env`; значения фиксируются в `protocol.json`.
Горизонты 7/14/30 — фиксированный контракт продукта.

`uv run --locked demon-plus baseline` создаёт в `artifacts/baseline`:

- `eda.json`: размеры, пропуски, статусы, месячные объёмы, отобранные категории;
- `protocol.json`: даты, категории, версии библиотек, хеши кода и входных файлов;
- `predictions.csv`: origin, date, step, category, model, actual, prediction;
- `metrics.json`: дневные и суммарные ошибки, разбивка по категориям и срезам;
- `report.md`, `eda.png`, `baseline_forecast.png`: отчёт и графики.

Повторный запуск обновляет только генерируемые результаты. В Git сохранён небольшой
снимок отчётов в `docs/results`; исходные данные и подробные прогнозы остаются локально.
